# 가라오케 자막(STT 기반) 기능

발표자 노트 음성(AI TTS로 생성했든, 사람이 녹음했든)을 텍스트로 인식해, 발표 중 재생 시간에 맞춰
단어를 하나씩 하이라이트하는 자막을 보여준다. **발표(▾) 버튼 옆 발표 옵션**에서 자막을 미리 켜두면
발표가 시작되기 전에 STT를 준비해두고, 발표 모드 좌하단 나레이션 컨트롤의 `CC` 버튼으로도 발표
도중 켜고 끌 수 있다.

## 사용 흐름

1. 슬라이드 노트 패널에서 노트를 쓰고, AI 음성을 생성하거나(✨ 나레이션 음성) 직접 녹음/업로드한다.
2. 툴바의 **발표 ▾** (발표 옵션) 드롭다운에서 **자막 → 카라오케(STT)** 를 선택해둔다. (API 키가
   없으면 이 시점에 AI 설정창이 뜬다 — 발표를 시작한 뒤에야 실패를 알게 되는 것을 막기 위함.)
3. **발표** 버튼(F5)으로 시작하면, 시작 슬라이드에 음성이 있고 아직 전사되지 않았을 때만 로딩
   화면에 "자막 준비 중..."이 잠깐 표시되고, 그 슬라이드의 STT가 끝나면 발표가 시작된다(§ 타이밍
   참고). 화면 하단에 카라오케 자막이 표시되고, 활성 단어는 노란색으로 강조된다.
4. 발표 도중에도 나레이션 컨트롤(좌하단)의 `CC` 버튼으로 즉시 켜고 끌 수 있다 — 미리 켜두지
   않았어도 발표 중 결정할 수 있다(다만 이 경우 그 슬라이드는 사전 준비가 안 됐으므로 잠깐의
   로딩 지연이 있을 수 있다).
5. 생성된 자막은 **프로젝트 데이터에 저장**된다(§ 저장·공유 참고) — 노트/노트 음성과 같은 급으로
   `.flatproj` 저장, 프로젝트 열기, 공유 링크에 실려 이동한다. **음성이 교체되기 전까지 계속
   유지**되고, 음성을 재생성/재업로드/삭제하면 그 즉시 무효화되어 다음 발표에서 자동으로
   다시 전사된다.

## 자막 준비 타이밍

처음 구현은 "CC를 누른 그 슬라이드만" 그때그때(lazy) 전사했다 — 슬라이드를 넘길 때마다 몇 초의
공백 뒤에 자막이 뒤늦게 나타나는 문제가 있었다(발표 중간부터 자막이 뜨는 것처럼 보임). 검토한
세 가지 타이밍과 최종 선택:

1. **그때그때(최초 구현, 폐기)** — 지연이 매 슬라이드마다 발생. 발표 시작은 가장 빠르지만 화면상
   끊김이 반복된다.
2. **발표 시작 전, 덱 전체를 다 기다림** — 사용자가 처음 제안한 방식. 발표 중 끊김은 완전히
   사라지지만, 슬라이드가 많은 덱은 "발표" 버튼을 누른 뒤 몇십 초씩 로딩 화면만 보게 된다 —
   발표 시작 자체가 늦어지는 것도 사용자 경험상 나쁘다.
3. **시작 슬라이드만 선행 대기 + 나머지는 발표 진행 순서대로 백그라운드 준비(채택)** — 로딩
   화면은 "지금 보게 될 슬라이드 하나"만 기다리므로 시작 지연이 거의 없고(대개 1~3초), 이후
   슬라이드는 `presentationOrder()`(현재 슬라이드 → 끝 → 처음부터 순환)로 미리 준비되기 때문에
   실제 발표 속도(슬라이드당 최소 수십 초~수 분)보다 훨씬 빠르게 캐시가 채워진다. 결과적으로
   체감상 2번과 동일한 매끄러움을, 시작 지연은 1번에 가깝게 얻는다.
   - 선행 대기는 최대 10초(`CAPTION_PREFETCH_TIMEOUT_MS`)로 제한한다 — STT가 이례적으로 느려도
     발표 시작 자체가 무한정 막히지 않고, 못 끝난 경우 해당 슬라이드는 화면에 뜬 뒤 마저 로딩된다.
   - Shift+F5(현재 페이지부터 발표)도 고려해 시작 인덱스를 기준으로 순서를 계산한다 — 항상
     0번부터 준비하지 않는다.
   - 같은 오디오를 백그라운드 준비·현재 슬라이드 표시·수동 CC 토글이 동시에 요청할 수 있어,
     `transcriptCache.getOrFetchTranscript()`가 진행 중인 요청을 재사용해 중복 STT 호출(과금 낭비)을
     막는다.
4. **더 이른 타이밍(검토했으나 채택 안 함)** — 노트 패널에서 음성을 생성/업로드한 직후, 편집
   화면에 있을 때 미리 전사해두는 방안도 검토했다. 발표 시작 시점의 지연을 이론상 0으로 만들 수
   있지만: (a) 발표를 아예 하지 않거나 자막을 안 쓸 덱까지 API 비용이 나간다, (b) 노트/음성을
   자주 바꾸는 편집 중에는 캐시가 계속 무효화돼 낭비가 커진다, (c) "자막을 쓸지"를 사용자가
   아직 결정하지 않은 시점에 선제적으로 돈을 쓰는 셈이라 명시적 옵트인(발표 옵션에서 자막 선택)
   원칙과 맞지 않는다. 그래서 "자막을 켜기로 결정한 시점(발표 옵션 선택 또는 발표 시작)" 이후로
   미뤘다.

## 사용한 API와 선택 이유

- **OpenAI `/v1/audio/transcriptions`, 모델 `whisper-1`.**
  단어 단위 타임스탬프(`timestamp_granularities=word`)를 지원하는 OpenAI 호스팅 모델은 이 저장소
  조사 시점(2026-08) 기준 whisper-1이 유일하다. `gpt-4o-transcribe` / `gpt-4o-mini-transcribe`는
  전반적인 인식 정확도는 더 높지만 `verbose_json`과 타임스탬프 세분화를 지원하지 않아, 가라오케처럼
  단어 단위 타이밍이 필요한 용도로는 쓸 수 없다.
- 이미 이 저장소가 OpenAI 키(TTS·이미지·챗 공용, `src/core/OpenAIClient.js`)로 통합돼 있어, 같은 키로
  바로 쓸 수 있는 OpenAI STT를 선택했다. 별도 STT 벤더(Deepgram, AssemblyAI, Google/Azure STT 등)는
  키·과금 계정이 추가로 필요해 이번 범위에서는 제외했다 — 다만 `SttClient.js`의 `transcribeSpeech()`
  시그니처(`Blob → {text, words}`)는 다른 벤더로 교체해도 호출부(`FlatPresenter`, `KaraokeCaptions`)를
  건드리지 않도록 의도적으로 벤더 중립적으로 설계했다.
- 업로드 제한 25MB, 지원 포맷(mp3/mp4/m4a/wav/webm/ogg/flac 등)은 OpenAI 문서 기준.

## 정확도 측정 방법론

`scripts/measure-stt-accuracy.mjs`로 두 가지 방식을 지원한다.

1. **왕복(round-trip) 모드(기본)** — 발표자 노트 스타일 한국어 샘플 문장을 OpenAI TTS로 음성화한 뒤
   whisper-1로 다시 전사해 원문과 비교한다. 사람이 정답 스크립트를 만들 필요가 없어 반복 실행하기
   쉬운 회귀 테스트에 가깝다. **단, "깨끗한 OpenAI TTS 음성"에 대한 정확도**이며, 실제 사람이
   녹음한 나레이션(주변 잡음, 발음, 마이크 품질, 사투리 등)의 정확도를 그대로 대변하지는 않는다.
2. **manifest 모드** — 실제 녹음 파일 + 사람이 만든 정답 텍스트 쌍(JSON)을 주면 그 오디오를 그대로
   전사해 비교한다. 실사용에 가까운 정확도를 재려면 이 모드를 쓴다.

두 모드 모두 다음 지표를 낸다(`src/core/karaoke.js`):

- **WER(Word Error Rate)** — 공백 기준 토큰 단위 편집거리 / 정답 단어 수. 영어권에서 흔히 쓰는 표준
  지표.
- **CER(Character Error Rate)** — 문자(코드포인트) 단위 편집거리 / 정답 글자 수(기본은 공백 제외).
  한국어는 형태소 경계가 공백과 정확히 일치하지 않아(예: 조사 결합) WER만으로는 오차가 부풀려질 수
  있다 — CER을 보조 지표로 함께 본다.

```bash
OPENAI_API_KEY=sk-... node scripts/measure-stt-accuracy.mjs
OPENAI_API_KEY=sk-... node scripts/measure-stt-accuracy.mjs --manifest samples/manifest.json --out report.json
```

이 저장소의 실행 환경에는 `OPENAI_API_KEY`가 없어 이번 변경에서 실제 API를 호출해 수치를 내지는
못했다 — 위 명령을 키를 가진 환경에서 직접 실행해 확인해야 한다. 대신 WER/CER 계산 로직 자체는
`src/test/karaoke.test.js`에서 알려진 편집(치환/삽입/삭제) 케이스로 단위 테스트했다.

## 자막 줄 나누기(karaoke.js)

단어 배열을 화면에 함께 표시할 자막 줄(cue)로 묶을 때, 다음 기준 중 먼저 오는 것으로 끊는다:

- 단어가 문장부호(`. ! ? … 。`)로 끝남 — whisper-1은 대개 문장부호를 단어에 그대로 붙여 반환한다.
- 이전 단어와 1초 이상 침묵(문장부호가 없는 구간을 보완).
- 자막 줄이 최대 단어수(기본 10)에 도달.

한국어 종결어미(다/요)만으로 문장 끝을 판단하지는 않는다 — "근데요", "그래요"처럼 문장 중간에도
흔히 나타나 오탐이 많기 때문이다.

## 저장·공유 — 자막은 어떻게, 어디에 남는가

노트/노트 음성처럼 자막도 **페이지 데이터의 일부**로 flatStore에 저장된다
(`pageNotesCaptions` = `{ words, text, language?, duration?, forRef }`). `forRef`는 "이 자막이
어떤 음성(idb:// 참조)을 위해 생성됐는지"를 가리키며, 자막의 유효성 판단 기준이 된다.

- **음성이 바뀌면(재생성/재업로드/녹음/삭제) 자막은 즉시 사라진다** — `setPageNotesAudio`/
  `applyAudioToPages`가 새 음성을 반영하는 바로 그 순간 `pageNotesCaptions`를 함께 지운다. 별도
  스테일 판정(해시 비교 등)이 필요 없다: forRef가 곧 그 음성 자체의 식별자이기 때문이다.
- **`.flatproj` 저장/열기, 공유 링크에도 실린다** — `ProjectSerializer.serializeProject()`가
  페이지 데이터를 통째로 zip에 넣기 때문에 별도 배선 없이 자동으로 포함된다. 단, `forRef`(idb://
  참조)는 노트 음성 자체(`notesAudio`)와 마찬가지로 브라우저 로컬 IndexedDB 키라서, 저장 시
  `media/` 파일로 옮기고 다시 열 때 새 idb 키로 재발급하는 과정에서 **`notesAudio`와 `forRef`를
  함께 리매핑**해야 계속 짝이 맞는다 — 이 부분을 놓치면 저장 후 다시 열었을 때 유효한 자막인데도
  "음성이 바뀐 것"으로 오판해 불필요하게 재전사하게 된다(`ProjectSerializer.js`에서 `notesAudio`를
  리매핑하는 바로 옆에서 `notesCaptions.forRef`도 함께 리매핑해 해결했다).
- **발표 중 만들어진 자막이 편집기에서 한 번도 안 연 페이지의 것이어도** 저장된다 — 백그라운드
  프리페치는 편집기 방문 여부와 무관하게 덱 전체를 훑기 때문에, `setPageNotesCaptions`가 필요하면
  (`getAllPagesAsync`가 만든 페이지 스냅샷으로) 페이지 캐시 항목을 새로 만든 뒤 자막을 저장한다.
- **캐시는 두 겹**이다: 프로젝트 데이터(위)가 1차 소스이고, 그 아래에 세션 한정 localStorage
  캐시(`transcriptCache.js`)가 같은 세션 안에서의 중복 STT 호출을 한 번 더 막아준다 — 하지만
  이건 없어도(예: 다른 브라우저, 캐시 삭제) 프로젝트 데이터만으로 완전히 동작한다.

이 동작은 `src/test/pageNotes.test.js`(플로우 스토어 단), `src/test/projectSerializerCaptions.test.js`
(저장/공유 왕복 단)에서 단위 테스트했고, 실제 브라우저에서도 확인했다: 자막을 한 번 만든 뒤
localStorage STT 캐시를 통째로 지우고 다시 발표해도 STT를 재호출하지 않고 즉시 같은 자막이
뜨는 것, 그리고 음성을 교체한 뒤에는 자동으로 재전사되는 것.

## 알려진 한계 / 다음 단계

- whisper-1은 화자 분리(diarization)를 지원하지 않는다 — 발표자 1인 나레이션을 전제로 한다.
- 단어 타임스탬프 자체의 정밀도(예: ±100ms 오차)는 API가 검증 수단을 제공하지 않아 이 도구로 직접
  측정하지 않는다. 텍스트 정확도(WER/CER)만 측정한다.
- `.flatproj`를 JSON(v1, 비-zip) 형식으로 직접 다루는 경로는 애초에 idb 참조 리매핑을 하지 않는다
  (media를 분리하지 않는 구형 포맷) — notesAudio와 마찬가지로 브라우저 로컬에서만 유효하다.
